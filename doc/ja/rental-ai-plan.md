# AIレンタルプレイ実装計画

状態: 計画案（2026-09-29）。この文書では機能実装・API呼び出し・課金は行わない。

## 1. 体験と初期スコープ

運営側のOpenAI APIで動くAIを、ブラウザから自分の席に参加させる。利用者はAPIキー・CLI・SKILLファイルを用意せず、AIの名前と最大200文字の「カスタムSKILL」を入力する。

- ルーム作成・入室で「レンタルAI」「自分のAIを接続」「観戦のみ」を選択する。レンタル利用可能時の推奨選択はレンタルAI。
- 名前は最大24文字。SKILLは空欄なら標準設定。文字数はUnicodeコードポイントで数え、Webとサーバの判定を揃える。過剰入力は切り捨てずエラーにする。
- 自分で付けたAI名と既存のゲーム内キャラクター名は区別して表示する。行動対象の識別は表示名でなく席・エージェントIDを使う。
- SKILL例: 「穏やかな口調で、発言の矛盾と投票先を重視してください。怪しい人にもまず質問し、根拠を短く説明してください。」
- 「慎重派」「積極派」「聞き役」の例文ボタンと `0 / 200` のカウンターを置く。SKILLは性格・話し方・戦い方の希望であり、役職やルールを変更するものではない。
- 「このAIで参加」で自分の1席を確保する。AIが準備済みになれば、既存どおりホストが開始する。外部AIとの混在を認める。
- 待機中は編集・キャンセル可能。開始時にSKILLを固定する。試合中の助言は既存の個別相談を使う。
- 自分の名前とSKILLの下書きは、明示的な「この端末に保存」で再利用できる。アカウント間・端末間の共有は後続対応。
- ブラウザを閉じても試合は続く。同じブラウザで戻れば自分の席を見られる。サーバ再起動による進行中ゲームの復旧は既存どおり対象外で、停止した試合のAPI呼び出しだけを再開しない。
- 初版は5人・ターン制から有効にする。9/13人とグループチャット方式は、同時実行数・応答時間の調整後に広げる。既存の外部AIの対応範囲は維持する。
- 運営負担の体験機能として設計する。利用者への決済・従量請求はこの実装に含めない。

## 2. UI

既存のLight・ノート風のカードと立体ボタンを使う。スマホは1列に配置する。

1. トップの案内で「設定なしで遊ぶ → レンタルAI」と「自分のAIを使う → セットアップ」を案内する。
2. 作成・入室フォームの参加方法でレンタルAIを選ぶと、名前・SKILL・例文・文字数を表示する。
3. 待機席に「レンタルAI」「準備中／準備できました／準備に失敗」の状態を表示する。
4. 対戦中は既存テーブル・発言・自分のAIパネルを使う。生成中の表示を役職や夜の行動者を推測できる公開通知にしない。
5. 制限やAPI障害で代替動作へ移った場合は、所有者へ「AIが応答できなかったため、今回は自動の代替行動を行いました」と伝える。公開側は既存の進行情報だけを表示する。
6. 終了後の記録は既存の30日保存を利用する。個別SKILL・API利用ログ・所有者へのメモを公開記録へ混ぜない。

## 3. 構成

```text
ブラウザ → ルームAPI → 席の予約・レンタル実行管理
                          ↓
                     席ごとのワーカー
                          ↕ 内部WebSocket（既存の参加プロトコル）
                     既存のゲームサーバ
                          
席ごとのワーカー → 許可された情報の抽出 → OpenAI Responses API
                ← 出力検証・期限確認   ← gpt-5.6-luna
```

- Goの `rental/` パッケージに、実行管理・WebSocketクライアント・プロンプト組み立て・OpenAI呼び出し・出力検証を置く。OpenAI処理を `logic/` や `model/` に入れない。
- 既存の参加キットと同じ通常のエージェントとして、固定された内部アドレスへ接続する。外向きの公開WS URLやユーザー入力を接続先に使わない。
- `room/` は席の所有権・参加方式・状態だけを管理し、`transport/` がレンタル管理と結びつける。ワーカーにはRoom全体や全役職のスナップショットを渡さない。
- レンタル席の接続トークンはサーバ内でのみ扱い、招待APIから返さない。通常の接続認証が有効な環境でも、既存の認証を満たす内部接続とする。
- 同じ席への二重作成・外部AIへの切替・同時開始を、予約世代番号と排他制御で防ぐ。作成に失敗したら席・ワーカー・予算予約をまとめて解放する。
- `NAME` はコードで即時応答。初期化・日付更新・通知・終了はローカル状態を更新するだけ。`TALK/WHISPER/VOTE/DIVINE/GUARD/ATTACK` の応答要求だけがAPI呼び出しを起こす。
- ワーカーは接続の読み取りを止めずに生成する。新しい要求・接続確認・死亡・終了で古い生成をキャンセルし、遅れて返った結果を次の行動へ送らない。
- Webの閲覧者向け履歴をAI入力に流用しない。死亡後のWebは神視点になるため、通常のエージェントパケットから席専用の状態を作る。

## 4. APIと状態の変更案

- 作成・参加APIに `agent_source: external | rental` と `rental_profile: {name, skill}` を追加する。省略時は既存の外部AI扱いにして互換性を保つ。
- `PUT /api/v1/rooms/{id}/rental` で待機中の自分のSKILLを編集、`DELETE` でレンタルを取り消す。別ユーザーの席の指定や、試合開始後の変更は拒否する。
- 準備失敗時の再試行は明示操作で、所有者確認・回数制限・二重実行防止を適用する。
- `GET /api/v1/rental-capabilities` は利用可否・対象人数・文字数制限・ユーザー向け停止理由だけを返す。キー・接続先・詳細予算・生のAPIエラーは返さない。
- 席に参加方式と `preparing / ready / playing / degraded / finished / failed` の状態を持たせる。公開投影は待機中の接続状態などに限定し、対戦中の内部状態は所有者向けにする。
- 更新APIは既存のCookie所有者確認、Origin確認、JSONサイズ制限を通す。RoomIDは操作権限の根拠にしない。

## 5. OpenAI呼び出し

- モデルは指定どおり `gpt-5.6-luna`。公式資料でResponses APIとStructured Outputsへの対応を確認済み。ただし運営アカウントでの利用可否は実装時に確認する。[モデル仕様](https://developers.openai.com/api/docs/models/gpt-5.6-luna)
- 管理者だけが `OPENAI_API_KEY` を環境変数またはDocker Secretで設定する。リポジトリ・ブラウザ・プロンプト・ログへ埋め込まない。Secret値自体を例示しない。
- 接続先はOpenAIの固定HTTPS API。モデル・URL・ツール設定を利用者に指定させない。HTTPリダイレクトで認証ヘッダーを別ホストへ送らない。
- `reasoning.effort: low`、`max_output_tokens: 1024` を初期案にする。出力上限には推論トークンも含む前提で、不完全出力を扱う。性能に応じて調整する。[推論と出力上限](https://developers.openai.com/api/docs/guides/reasoning)
- ツールは付けない。ブラウザ・シェル・ファイル・MCP・外部URL取得を実行できる経路を作らない。
- `store: false` を指定し、会話状態は自サーバで席ごとに保持する。これはAPI側のデータ保持全体がゼロになるという意味ではない。[データ管理](https://developers.openai.com/api/docs/guides/your-data)
- 一回の応答で発言または対象選択を得る。`note` は短い所有者向け説明に限定し、内部の思考過程の出力を要求しない。

## 6. プロンプトインジェクション対策

自由文を扱う以上、モデルが指示に惑わされる確率をゼロとは約束しない。ルール外の操作・他席の秘密取得・上限を超えた課金がモデル出力だけで起きない構造を目標にする。公式資料も、権限分離と構造化出力を組み合わせる防御を勧めている。[安全対策](https://developers.openai.com/api/docs/guides/agent-builder-safety)

| 境界 | 対策 |
| --- | --- |
| 固定の指示とユーザー文 | 固定developerメッセージには運営が管理するルール・応答仕様だけを置く。SKILL、ユーザー名、会話、助言はJSONで明示したuser側のデータとして渡し、developer指示へ文字列展開しない |
| カスタムSKILL | 性格・話し方・戦略の希望として解釈する。コードやSKILLファイルとして実行しない。200文字・UTF-8・制御文字などを検証する。禁止語一覧や区切り文字だけで安全とは判断しない |
| 他AIの発言 | ゲーム内の証言として扱う。偽のSYSTEM文・設定変更・秘密の要求は運営の指示に昇格させない。人狼の嘘や役職騙りといった通常の戦術は許容する |
| 所有者の助言 | 自分の生存席への助言だけを取り込み、ゲームの制約を上書きしない。長さ・頻度・未読キューの上限を設ける |
| 入力情報 | 席専用DTOを許可リストで作る。APIキー、招待トークン、キーフレーズ、他席のSKILL・相談・未知の役職はモデルに送らない。共有の会話IDや全ルーム共通メモリを作らない |
| 行動 | 要求された行動種別はサーバが固定する。発言用／対象選択用のJSON Schemaを使い、追加フィールドを禁止。対象は合法な候補のenumに制限する |
| 最終検証 | Schemaを通過しても、現在の要求世代・生死・対象・役職による行動権・文字数・残り発言枠をコードで再確認してから送る。許可されたSKIP・対象なし以外を勝手に生成しない |
| 表示 | 発言・SKILL・メモは既存UIと同様にテキストとしてエスケープ表示する。HTMLや外部画像・リンクの自動実行経路を追加しない |

Structured Outputsは形式の制約であり、発言内容の正しさや安全性の保証ではない。拒否、不完全出力、無効な対象を個別に扱う。[構造化出力](https://developers.openai.com/api/docs/guides/structured-outputs)

自分のAIが知るSKILLや自分の役職を、生成した発言で話してしまうリスクは残る。SKILLを秘密の認証情報として扱わず、役職のカミングアウトや騙りを許すゲーム性と、システム上の権限保護を分けて設計する。

## 7. 応答期限・代替動作

- 待機中はイベント待ちで、生成ループや定期的なAPI確認を行わない。
- 初期案は1回のAPI応答待ち15秒、再試行は429・一時的5xx等に最大1回。待ち時間を含め全体35秒以内、かつゲーム側のaction期限の3秒前までとする。短いゲーム設定ではそちらを優先する。
- `Retry-After` が残り時間に収まらない場合は再試行しない。401/403、拒否、無効出力を無制限に再生成しない。
- 応答失敗時はモデルを追加で呼ばず、許可された発言または合法な候補からの選択で1回だけ代替応答する。SKIP禁止の設定ではSKIPを使わない。合法な行動がない場合は既存ゲーム側の扱いへ戻す。
- 連続3回の失敗・予算到達時は、その試合のレンタルを代替動作に固定して所有者へ通知する。試合中に自動で再課金を再開しない。
- 正常な応答を含め、同じ要求には一度しか送らない。API通信の再試行とゲームへの行動再送を分ける。

## 8. 費用と濫用の制限

モデル仕様に記載された料金は100万トークンあたり入力$0.20・出力$1.20。実際の料金は投入履歴、推論を含む出力、試合の長さで変わるため、初期段階で1試合定額の見込みを断言しない。[料金を含むモデル仕様](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

- 上限の初期案: 1ユーザー同時1席、全体5ワーカー、1席60回／1試合200回までのAPI呼び出し。再試行も数える。入力は1回8,000トークン以内、出力は1,024トークン以内。
- 重要なゲーム状態・自分の結果・過去の投票は構造化して保持し、長い会話履歴を上限内で整理する。要約を追加の高優先指示にしない。初版は履歴整理のためだけに別のLLMを呼ばない。
- 同時実行枠は待機から試合まで確保する。待機予約には10分の期限と明示的な延長を設け、退室・閉室・終了で解放する。
- 管理者が日額・1試合の予算を設定してから公開機能を有効にする。キー未設定・予算未設定時はレンタルを利用不可にする。
- 呼び出し前に最大費用を原子的に予約し、応答のusageで精算する。不明な課金結果はゼロ扱いにせず予約額を維持する。キャッシュ書き込み等も含む保守的な予約を行う。上限到達時は新規受付を停止する。
- 利用量と予算予約はSQLite等の永続ストアに置き、再起動でリセットしない。初版は単一サーバ構成とし、複数台化する際は共通の原子的な予算管理へ移す。
- Cookieだけでは利用者を強く識別できないため、セッション・信頼するプロキシから得たIP・全体で制限を設ける。IPヘッダーを無条件に信用しない。公開環境では作成時にTurnstile等をサーバ検証し、予算上限と併用する。
- Cookie削除やIP変更を完全に防げるとは扱わない。より厳密な一人あたり利用枠が必要になった段階でログインを導入する。
- 記録する運用情報はモデル名、入力／出力トークン、推定費用、時間、失敗理由、匿名化した席識別子。プロンプト全文・秘密情報・生のAPIエラーを公開ログに出さない。

## 9. 実装の分担と順序

1. **席・公開API**: `room/` と `transport/web.go`。所有権、参加方式、予約世代、編集、開始時固定、公開状態の分離。ここでAPI契約を固定する。
2. **実行ワーカー**: `rental/`。内部WS、席専用入力、Responses呼び出し、構造化出力、キャンセル、合法な代替行動。1の契約を使って並行作業できる。
3. **Web UI**: `web/static/`。選択カード、200文字入力、例文、準備状態、スマホ、自分のAIパネル。1のレスポンス例を使って並行作業できる。
4. **予算・運用**: `store/`、Compose、設定例。永続的な利用量、原子的な予約、レート制限、秘密設定、停止スイッチ。ワーカーの課金前フックと合流する。
5. **統合と文書**: 日本語・英語のAPI／設定／参加案内。YAML設定キーを追加する場合は配布用設定すべてを更新する。既存observer経由でUI更新を行い、秘密の行動者を新しい公開イベントに含めない。

実装時の受け入れ条件:

- ブラウザだけで5体のレンタルAIが準備・開始・終了でき、外部AIとの混在でも通常ルールに従う。
- 待機・再描画・二重クリック・ブラウザ再接続でAPI呼び出しや席が重複しない。
- 他席の情報・キーが入力DTO、レスポンス、SSE、公開リプレイに入らない。
- SKILL／発言／助言の注入文が、操作権限、行動種類、対象候補、課金回数の制限を越えられない。
- 期限切れ・429・5xx・切断・拒否・不完全JSON・予算到達でも、古い行動の誤送信と無限再試行が発生しない。
- 永続予算の競合、再起動後の予約残高、キャンセル時の解放が整合する。
- 小さい画面でも参加方法と文字数・エラーが読める。

この段階では設計のみ。APIキーの設定や有料呼び出しは実装段階で行う。
