# Web UI 設計・SubAgent 実装指示

[English](../en/web-ui-design.md)

ステータス: 実装前の提案仕様。2026-09-28。現行コードに存在する機能と、これから実装する契約を区別する。本書はWeb UI担当とバックエンド担当の共通仕様とし、モックの動作をサーバ実装済みと扱わない。

## 1. 目的と決定事項

人間がWebで部屋を作り、自分や友達のAIを招待し、自分のAIの視点から会話を読み、必要なら個別に相談する。自分のAIが死亡すると神視点になり、試合終了後も会話を読み返せる。

- Web・HTTP API・SSE: 8080。AIのゲーム用WebSocket: 8081。
- Lightのみ。OSがDarkでも背景・入力・ダイアログをLightに固定。テーマ切替UIは作らない。夜フェーズでも配色全体を暗くしない。
- 「Noteチック」は参考サイトに合わせ、紙のノート・付箋・押せる立体ボタンとして解釈する。
- 人間はユーザー名を入力して参加する。表示名、内部UserID、席ID、AgentID、RoomID、GameIDを分ける。
- 初期の人数は5・9・13人。人数に対応するプリセットを読み込む。ルールの選択肢はサーバが提供する対応済みの組み合わせだけにする。
- 待機中は部屋主が開始操作。生存中は自分のAIが知る情報のみ、死亡後は神視点。部屋主に秘密情報の特権を与えない。
- 人間はAIへ助言できる。ゲーム上の発言・投票・能力行使はAIが既存ルールに従って行う。
- 初期版は1部屋1試合。「もう一度」は新しい部屋を作り、席・招待・キーを再発行する。

## 2. 参考デザインと独自の調整

参考: [BioQuiz](https://bioquiz.yokohide0317.workers.dev/)。公開HTMLと、そこから参照される[ノート用CSS](https://bioquiz.yokohide0317.workers.dev/_astro/notebook.BPoVH1l-.css)を確認した。通常の`/css/style.css`に後段のノート用CSSが上書きする構成なので、前者だけを参考にしない。CSSのハッシュ付きURLは将来変わりうる。

確認できた特徴は、クリーム系の背景、方眼、濃い輪郭、パステルのアクセント、紙の段差、4〜5pxの硬いボタンの影と押下時の沈み込み。以下の色・寸法・レイアウトは本プロジェクト向けの提案値であり、参考サイトの完全な複製ではない。ブラウザの画面取得が利用できなかったため、参考サイトの見た目をスクリーンショットで検証したものではない。

デザインの呼び名は「AI人狼の観戦ノート」。仮の画面名は「人狼ノート」、補助表記は「AIWOLF」。ブランド名は一箇所で変更可能にする。

| 要素 | 方針 |
| --- | --- |
| ページ背景 | 温かいクリーム色と、ごく薄い26px方眼 |
| 主なパネル | 白に近い紙色、濃い輪郭、下側に紙が重なる薄い影 |
| 見出し | 太めの日本語ゴシック。本文は読みやすい通常のゴシック |
| 操作 | ミント色の立体ボタン。白い副ボタンにも小さな段差 |
| 状態 | 色＋アイコン＋文字。付箋は意味のあるラベルに限定 |
| 会話 | 本文の裏は無地。左揃えの発言録。長文と日本語を読みやすく |
| 装飾 | 方眼は外周、穴・赤い余白線は表紙や大きなノート外枠だけ |

ボタンの動きと紙の質感に個性を集める。すべての発言に太い枠や影を付けない。操作対象でないカードは浮き上がらせない。秘密の役職が色・画像・並び順・CSSクラスから推測できる装飾を使わない。

## 4. 立体ボタンの仕様

高さ48px、大きな開始・作成ボタンは52px。小さな見た目のコピーボタンもタッチ領域44px以上。横padding 18〜24px、角丸12px、輪郭2px。主要操作は同じ領域に原則1つ。

| 状態 | 主要ボタンの見た目・挙動 |
| --- | --- |
| 通常 | ミントの面、濃い文字、下に5pxの硬い影 |
| hover | 1px持ち上がり、影6px。hover可能な機器のみ |
| active | 下へ4px、影1px。レイアウト自体は移動しない |
| focus-visible | 外側に青い3px輪郭、offset 3px。影とは別に表示 |
| disabled | 紙のくぼみ色、読めるグレー文字、影1px。周囲に無効理由を表示 |
| loading | 幅を固定し「作成中…」等に変更、二重送信不可 |

## 5. 画面・URL・レイアウト

| URL | 内容 |
| --- | --- |
| `/` | 部屋作成・RoomID入力・この端末で参加した部屋 |
| `/rooms/new` | 部屋作成フォーム |
| `/rooms/:roomId` | 未入室ならユーザー名入力、入室後は待機室→対戦→結果 |

観戦URLは状態が変わっても維持する。深いURLへの直接アクセス・リロードもGoサーバから正しく返す。存在しない部屋・閉室・中断を別の状態として表示する。

### PC: 1200px以上

最大幅1440px、左右32px、ヘッダ64px。対戦画面は220px / minmax(0, 1fr) / 320pxの3列、gap 24px。中央は最低480pxを確保。待機画面は主領域と幅320pxの招待・開始欄の2列。フォームは最大640px。

図の役職・占い結果は本人視点の例。公開視点には送信も表示もしない。図中の時計は実時刻で、ゲーム内の日付と区別する。

### タブレット: 768〜1199px

中央＋280pxの右欄、gap 16px。参加者は上部の「参加者 5」ボタンで開くパネルへ移す。幅が不足するときも会話の横スクロールは発生させない。

### モバイル: 767px以下

左右16px、ヘッダ56px。画面下に「会話」「参加者」「自分のAI」の3タブを固定し、一度に1パネルを表示。上部に日付・フェーズ・接続状態・視点をコンパクトに残す。

- 待機中のタブは「待機室」「招待」「ルール」。開始操作は待機室に配置。
- 未認証でも「自分のAI」タブは表示し、キーフレーズ入力へ導く。観戦者には「AI未登録」と説明する。
- 神視点になっても「自分のAI」の位置を維持。パネル内の視点表示と操作可否を更新。
- `100dvh`とsafe-areaを考慮。キーボード表示中に入力や送信ボタンが隠れないようにする。
- 各パネルのスクロール位置・未送信文をタブ切替で保持する。機密下書きはメモリ内のみ。
- 360px幅で横スクロールなし。13人の一覧や長い名前でレイアウトを壊さない。

## 6. 各画面の具体仕様

### 6.1 トップ

見出し「AIたちの議論を、同じノートで。」、補足「部屋をつくってAIを招待。あなたのAIの視点から、人狼ゲームを見届けよう。」。大きな飾りより作成・入室の操作を上部に置く。

- 主要操作「ルームを作る」。副領域はラベル付き「RoomID」入力と「ルームを開く」。
- 下に「この端末で参加したルーム」。各行は名前、RoomID、状態、更新時刻。初期状態は「まだ参加したルームはありません」。
- 全ルームの公開検索は初期版に含めない。ブラウザの最近履歴だけで部屋への権限を得られることはない。

### 6.2 作成フォーム

1枚のノート内で、上から「あなたの名前」「ルーム名」「参加AI数」「ルール」「参加方法」。

- ユーザー名: 1〜24文字、ルーム名: 1〜48文字。前後空白を除去し、Unicodeの数え方はサーバと一致させる。表示名は本人認証に使わない。
- 人数: 5 / 9 / 13のラジオカード。選択値をチェックと枠で示す。サーバが返す役職構成の合計も表示。
- ルール: 日本語の説明付きプリセット。未対応の人数×通信方式を選べない。初期値は5人・ターン制。
- 参加方法: 「自分のAIも参加する」を初期選択、「部屋を作って観戦する」も用意。観戦だけの部屋主には席を確保しない。
- 説明: 「AIが全員そろったら、あなたがゲームを開始できます。」
- 主要操作「ルームを作成」。入力エラーは項目の直下。サーバ拒否でも入力値を保持。
- 再送で部屋が増えないよう作成要求に冪等性キーを使う。

### 6.3 共有URLからの入室

入室前は部屋名・ルール・残席など、サーバが認める公開情報だけを表示。「あなたの名前」と「AIを参加させる / 観戦する」を入力する。

- 参加枠はAIの席数であり、観戦者数を含めない。
- 満室は「参加枠が埋まっています。観戦で入室できます」。開始済みは新しいAI席を作れない。
- 同名は入室を許可して短い識別サフィックスを表示。表示名の一致で他人の席を復元しない。
- 「参加する」の最終結果はサーバの原子的な席確保で決定。先に満席になった場合も入力名を保持。

### 6.4 待機室

部屋名・RoomID・「AI接続済み 3 / 5」を表示。席ごとに、人間の名前、AI名、接続状態、本人マークを表示する。空席は破線枠。

席の状態は「空席」「AI待ち」「接続確認中」「接続済み」「切断中」。人間の入室とAI接続を同じカウントにしない。

招待欄は次の2つを明確に分ける。

- 「友達を招待」: 秘密を含まないWebの共有URL。コピー完了を短く通知。
- 「自分のAIを接続」: 本人の席専用接続情報。「AIへの案内をコピー」で、接続先・RoomID・必要なプロトコル・キーの持ち主への伝え方をまとめる。部屋主でも他人の招待秘密を見られない。

コピー失敗時は選択可能なテキストを表示。「RoomIDだけでは通常のチャットAIは自動参加しない」と、接続ガイド内で説明する。

部屋主の「ゲームを開始」は、全席のAIが準備完了し、ルールが有効で、開始処理中でないときに有効。未充足時は「あと2体のAI接続を待っています」。他ユーザーには「部屋主の開始を待っています」。

開始要求中は人数変更・席移動を停止。サーバが開始に失敗したら理由と現在の席状態を再取得。初期版は作成後の人数・ルール変更を行わず、新しい部屋の作成で対応する。待機中の退出は確認後に席を解放する。

### 6.5 キーフレーズ入力

ゲーム開始時に会話は公開視点で表示を続ける。右欄に鍵アイコン付きの紙カードを置く。入力のために全画面を塞がない。

- 見出し「自分のAIの視点をひらく」。
- 説明「ゲーム開始後、あなたのAIが個別に伝えたキーフレーズを入力してください。」
- 1つの入力欄、貼り付け可。初期は伏字、表示切替あり。自動修正・大文字化を無効化。
- 主要操作「視点をひらく」。エラーは「キーフレーズを確認してください」。試行回数制限時は再試行可能時刻を表示。
- 成功後はキーを消去し、サーバのセッションと閲覧投影を再取得。「ハルの視点になりました」と通知。
- AI未接続、AI未対応、フレーズ未受領は接続ガイドへ誘導。Webに他人のキーや部屋主向けの万能キーは出さない。

キーは試合＋席＋所有者に結び付け、サーバが生成し、対応AIクライアントの個別経路で所有者へ渡す。AIクライアントのターミナルや私用チャット等への実装が必要。公開のゲーム発言として送らせない。初期版では同じ端末セッションで再読込可能、別端末への引継ぎは対象外。名前やRoomIDだけで所有権を復元しない。

### 6.6 対戦・公開会話

中央の「会話の記録」は、各発言にアバター、ゲーム内名、発言順、時刻、本文を表示。自分のAIには小さな「自分」ラベル。全発言左揃え。引用は元発言へのリンクと引用抜粋。

- 「公開会話」「出来事」で表示対象を切替。人狼視点では許可された「囁き」タブを追加し、対象が「人狼だけ」と明示。
- 日付・フェーズは付箋風の区切り。夜は青い「夜」ラベルに変わるだけでLightを保つ。
- 日付選択、発言者フィルタを提供。検索対象・件数はその閲覧者に許可された発言だけ。
- 公開イベントは追放・襲撃結果等、公開されるタイミングで表示。非公開能力行使や隠れたイベントの発生件数を公開画面に出さない。
- 会話の生HTMLは描画しない。初期版はプレーンテキスト＋改行、長いURLや連続文字は折り返す。
- 長文は原則全文表示。500文字を超える場合の折りたたみは明示的な「続きを読む」で、展開後も読み位置を維持。
- 自動追従は末尾から80px以内のときのみ。過去を読んでいる間は位置を保持し「新しい発言 N件 ↓」。日付フィルタ中は最新日への移動を明示。
- 再接続では同じイベントを重複表示しない。履歴の先頭への追加はスクロール位置を保つ。
- 毎秒の派手なアニメーションや発言ごとの通知音は入れない。

### 6.7 自分のAIパネル

上から「視点」「役職」「自分だけの情報」「AIへの相談」。公開視点では個別情報をロック説明へ置き換える。

- 役職は日本語名＋一文の説明。人狼だけ仲間の情報、占い師だけ通知済みの占い結果など、AIの知識と一致させる。
- 判定は「人間 / 人狼」等、実際の判定種別を表示。占い結果を相手の正確な役職へ変換しない。
- 推測・ユーザーの助言・AIの説明と、サーバが確定した結果を混同しない。「AIの見解」等のラベルを付ける。
- 思考過程の取得は要件にせず、AIが提供する短い方針・説明・質問を表示する。
- 自分の秘密情報に他ユーザー名が含まれても公開タイムラインには複製しない。

### 6.8 個別相談

相談先を「ハルにだけ届きます」と常時表示。チャットの背景は紙、ユーザーの助言は淡いミント、AIの説明は白。村の公開発言とはパネル・宛先を分ける。

- 入力は2〜5行、提案上限1000文字。Enterで改行、送信ボタンまたはCtrl/Cmd+Enterで送信。IME変換確定を送信扱いしない。
- 送信状態: 送信中→サーバ受付→AI受信。別に失敗・期限切れ・死亡による取消を表示。「受信」を「採用・反映」と表示しない。
- AIが対応する場合のみ「AIからの質問」を表示。質問ID、選択肢または自由回答、締切を持つ。期限はサーバ時刻との差分で表示し、期限後の採用可否はサーバが判定。
- 人間が返答しなくてもゲームは停止しない。説明文「回答がなければAIが判断します」。
- メッセージは送信IDと対象フェーズ・有効期限を持ち、再送でも重複配達しない。失敗時は下書きを復元し、明示的に再送する。
- 非対応AIでは入力を無効にして「このAIはWebからの相談に対応していません」。接続できたことと相談機能があることを分ける。
- 他人のAIへの相談、対戦中の人間同士の公開チャット、人間が直接投票するUIは初期版に含めない。

### 6.9 死亡・神視点

サーバの確定イベントで、相談欄を即座に無効化し、未配達の助言を失効。その後に神視点のデータを取得する。クライアントの表示切替だけで権限を変えない。

通知「ハルが死亡しました。これ以降は神視点で観戦できます。」。本人パネルに「死亡・観戦中」、画面上部に常時「神視点」。死亡は控えめなグレーと文字で表し、点滅やホラー演出はしない。

- 全役職とゲーム内の非公開イベントを閲覧可能。相談入力は閉じ、過去の自分との相談は読取専用。
- 「公開会話」「囁き」「全イベント」を選べる。権限変更時に古い投影キャッシュを破棄して履歴を再取得。
- 通常観戦者は他人の死亡で神視点にならない。全員が神視点になるのは試合終了後。
- 同一試合で生存AIへ再紐づけできない。未送信の相談文も削除し、自動送信しない。
- 神視点を参加AIへ配信しない。外部通話・別アカウントでの共謀までは防げないことは運用上の制約。

### 6.10 終了・中断・閉室

終了時は中央上部に「村人陣営の勝利」等の結果カードを追加し、全文を消さない。自分の陣営の結果、役職一覧、日付別履歴を閲覧可能にする。

- AIの全役職・ゲーム内秘密は解禁。人間とAIの個別相談、キー、認証情報は解禁しない。
- 「結果URLをコピー」「同じ設定で新しいルーム」を表示。コピーには私用相談や秘密トークンを含めない。
- 中断は勝利と区別し「接続エラーにより中断」「サーバ再起動により中断」等、公開可能な理由を表示。
- 初期案では中断を終端状態として全ゲーム情報を解禁。閉室が待機中なら役職情報はない。
- ログ保存期限はサーバ提供値を表示。未定の「永久保存」を約束しない。

## 7. 視点・操作のマトリクス

| 閲覧者 | 公開情報 | 自分の役職・知識 | 全役職・秘密履歴 | 自分のAIへ相談 | 開始操作 |
| --- | --- | --- | --- | --- | --- |
| 未認証の入室者 | 可 | 不可 | 不可 | 不可 | 部屋主かつ待機中のみ |
| 生存AIの所有者・キー認証済み | 可 | 可 | 不可 | 対応AIかつ進行中のみ | 不可 |
| 死亡AIの所有者・キー認証済み | 可 | 可 | 可 | 不可 | 不可 |
| 通常観戦者 | 可 | 不可 | 不可 | 不可 | 部屋主かつ待機中のみ |
| 終了・中断後の入室者 | 可 | ゲーム情報は公開 | 可 | 不可 | 不可 |

`owner`は部屋管理、`viewMode`は閲覧権限で、別軸。生存状況・フェーズ・権限はサーバが唯一の決定元。UIに任意のAgentIDで視点を選べる機能を置かない。

## 8. フロントエンド用データ契約（提案）

以下は新規設計で、現行APIの存在を意味しない。実装担当間で先に型とエラーを固定する。生の`GameSnapshot`や`BroadcastPacket`をそのままブラウザに渡さず、閲覧者用の投影を組み立てる。

```ts
type RoomStatus = 'waiting' | 'starting' | 'running'
  | 'finished' | 'aborted' | 'closed';
type ViewMode = 'public' | 'agent' | 'omniscient';

interface RoomProjection {
  roomId: string;
  gameId?: string;
  status: RoomStatus;
  version: number;
  serverTime: string;
  viewer: {
    userId: string;
    isHost: boolean;
    ownSeatId?: string;
    viewMode: ViewMode;
    permissions: {
      canStart: boolean;
      canClaim: boolean;
      canConsult: boolean;
      canSeeWhispers: boolean;
    };
  };
  participants: ParticipantPublic[];
  game?: GameVisibleState;
  privateAgent?: AgentPrivateView;
  cursor: string;
}
```

補助型は契約実装時に定義する。`ParticipantPublic`には許可されないroleを含めない。`AgentPrivateView`は本人用の知識のみ。未公開値は送信自体を省き、受信後CSSで隠す方式にしない。UI用のcursorは不透明な値とし、欠番から秘密イベント数が分からないようにする。

| API案 | 用途 |
| --- | --- |
| `GET /api/v1/room-presets` | 対応人数・ルール・相談可否の仕様 |
| `POST /api/v1/rooms` | 作成・部屋主セッション |
| `POST /api/v1/rooms/:id/join` | ユーザー名・参加/観戦・席確保 |
| `GET /api/v1/rooms/:id` | 入室前公開情報または閲覧者用投影 |
| `POST /api/v1/rooms/:id/agent-invitation` | 自分の席のAI接続情報 |
| `POST /api/v1/rooms/:id/start` | 部屋主による開始 |
| `POST /api/v1/rooms/:id/claim` | キーフレーズ照合・視点解放 |
| `GET /api/v1/rooms/:id/history?cursor=...` | 閲覧可能な履歴のページ取得 |
| `GET /api/v1/rooms/:id/events` | 待機状態・視点変更・ゲームイベントのSSE |
| `POST /api/v1/rooms/:id/consultations` | 自分のAIへの助言・回答 |
| `GET /api/v1/rooms/:id/consultations` | 自分の個別相談履歴 |
| `POST /api/v1/rooms/:id/leave` | 待機中の席解放・退出 |
| `POST /api/v1/rooms/:id/close` | 部屋主による待機室閉鎖 |

進行中の部屋を閉じる強制終了UIは初期版に含めない。更新APIのレスポンスは日本語の表示文と機械判定用コードを分ける。満席・二重開始は409、認証切れは401、権限不足は403、入力不正は400、制限は429、未存在は404を目安にする。

- UIは同一オリジンの8080 APIを利用。HttpOnlyのセッションCookieを使い、本番HTTPSではSecure。更新APIはCSRF対策・Origin検証を行う。
- SSEも同じセッションで認証し、URLにキーフレーズを入れない。接続時だけでなく配信時にも閲覧権限を適用。
- snapshotとcursorを一貫した時点で取得し、以降を購読。取り逃し時は再取得。視点変更・セッション変更では購読を張り直す。
- 公開用データ、本人用データ、相談のキャッシュを分離。機密レスポンスは`no-store`。秘密をlocalStorageや共有キャッシュに保存しない。
- 旧`/api/v1/games`、`/realtime`、TTS、ログ配信が迂回路にならないようバックエンドで保護または公開ルートから除外。
- AIとの相談はゲーム用WSの通常応答へ混ぜず、認証された別の制御チャネルを設計。AIの対応能力をハンドシェイクで確認。

## 9. コンポーネントと実装境界

初期方針はGoから配信するHTML/CSS/JavaScript（ES modules）。ランタイムとしてNodeを必須にしない。SubAgentが一部だけ異なるUIライブラリを持ち込まない。型定義は契約とドキュメントで保持し、TypeScriptを採る場合はビルド手順を統一する。

| コンポーネント | 責務 |
| --- | --- |
| AppShell / RoomHeader | レイアウト、部屋名、接続・視点・フェーズ |
| NotebookPanel / StickyLabel | 共通の紙と状態ラベル |
| RaisedButton / Field / CopyField | 操作、入力、コピー成功・失敗 |
| RoomCreateForm / JoinForm | バリデーションと作成・入室 |
| SeatList / SeatCard / InvitePanel | 席、AI接続、招待 |
| PerspectiveGate / PerspectiveBadge | キー入力と現在の視点 |
| ParticipantList / RoleBadge | 参加者と閲覧可能な役職 |
| Timeline / TalkEntry / SystemEvent | 会話と出来事、日付、追従 |
| PrivateKnowledgePanel | 自分だけの役職情報 |
| ConsultationPanel / QuestionCard | 個別相談、質問、期限、配達状態 |
| ResultPanel / ConnectionBanner | 結果・中断・再接続 |
| MobileTabs / Dialog / Toast | モバイルナビ、確認、短い通知 |

配置案: `web/static/`にCSS・JS・SVG・HTML、`web/`のGo埋め込みから配信。`transport/`は配信と認証、`orchestrator/`は部屋・権限・開始、`service/`と`observer/`はイベント投影と保存、`store/`は永続化、`model/`はビュー型。既存AGENTS.mdの依存方向を維持する。

`logic`はセマンティックなイベントと読み取り専用ビューをobserverへ渡す。Webのセッション、キー、Cookie、HTMLをゲームロジックへ持ち込まない。秘密を含む内部イベントと公開用イベントの境界を明確にする。

## 10. 状態・アクセシビリティ・エラー

- loading: 行の骨組みまたは「読み込み中」。役職の仮データを一瞬でも描画しない。
- 空の会話: 「ゲームが始まると、ここに会話が記録されます」。接続済みと進行中を区別する。
- SSE切断: 「接続を確認しています。表示は更新されていません」。最後の情報は保持し、操作可否は再確認。接続不明時の助言は送らず下書き保持。
- 履歴取得失敗: 既存履歴を残し「履歴を読み込めませんでした」「再試行」。
- セッション失効: 個別情報と相談を消去し、再入室へ。別ユーザーのセッションに古いDOM・キャッシュを残さない。
- フォーカスはルート遷移時の見出し、モーダル終了時の起点へ。新しい発言が来ても奪わない。
- フォームはlabel、補足、エラーを関連付け、`aria-invalid`を設定。radio・tabはキーボード操作可能にする。
- `aria-live=polite`で重要な接続・配達・視点変更を通知。会話全文を毎回読み上げず、必要なら新着件数を通知。
- 通常文字のコントラスト目標4.5:1、操作の境界・フォーカス3:1。実装時に実際の組合せを測定する。
- 色だけに依存しない。200%拡大、キーボード、モバイルの安全領域、OS Dark、reduce motionを確認。
- 不透明な覆いで役職を隠す実装は禁止。テキスト、アクセシビリティツリー、Network、DOM属性に漏れないことを検証。

## 11. SubAgentへの作業分割

最初に共通トークン、モック投影、API契約、状態名を確定してから並行作業する。各担当は自分のファイル範囲を守り、同じCSSやAPI型を独自に複製しない。

| 担当 | 作業範囲 | 成果物 |
| --- | --- | --- |
| A: 基盤・デザイン | tokens、共通部品、AppShell、responsive | ボタン全状態・紙・フォーム・タブの見本 |
| B: 部屋・入室 | トップ、作成、入室、待機、招待、開始 | 空席/満席/切断/開始中の画面 |
| C: 観戦・AI | 会話、本人情報、キー入力、相談、死亡、結果 | 全視点と再接続の画面 |
| D: バックエンド | ルーム・セッション・AI連携・権限・SSE・保存 | 合意したAPIと実クライアント結合テスト |
| 統合担当 | 契約調整、CSS/状態統合、全体QA | 1試合を完走するWeb体験 |

順序: AとDが契約・サンプルを用意→B/Cをモックで実装→実API接続→権限制御と対戦を結合検証→日英ドキュメント・Docker更新。

モックには必ず表示上「デモ」を付ける。実装のレビュー画像用に、公開視点、生存占い師、生存人狼、死亡者、終了、接続切れ、13人の固定データを用意する。プロダクションのクエリ文字列でviewModeを上書きできるデモ機構は作らない。

## 12. 完了条件

### 見た目

- 1440×900、1024×768、390×844、360×800で主要画面を確認し、スクリーンショットを残す。
- 紙・方眼・付箋・立体ボタンに一貫性があり、長い会話の本文は無地で読みやすい。
- ボタンの通常/hover/active/focus/disabled/loadingを確認。隣接要素が押下で動かない。
- OS Dark、夜フェーズ、神視点、終了画面もLightのまま。
- 長い日本語名、URL、13席、500文字以上の会話で横にはみ出さない。

### ユーザーフローと情報制御

- 2つの別セッションが同じ試合を異なるAI視点で閲覧でき、第三の観戦セッションには公開情報だけが届く。
- 名前の重複・他人のキーフレーズ・RoomIDの推測・URLの変更で他人の視点になれない。
- キー認証後、AIに実際に通知される知識と表示が一致する。人狼の仲間、占い結果の通知時期も確認。
- 死亡→相談停止・未配達取消→神視点の順がサーバ上で成立。送信との競合も検証。
- 観戦者や部屋主は誰かの死亡で神視点にならない。
- 旧API、SSE再接続、履歴、件数、DOM属性、ログ、TTSから秘密が漏れない。
- 再読込・SSE再接続後も会話の欠落・重複がなく、過去を読んでいる位置が維持される。
- 終了URLに再アクセスして結果を読める。個別相談とキーは公開されない。
- AI未対応時に相談欄が送れないこと、期限切れ・配達失敗・中断を確認。

### 実装検証

既存の`go build ./...`、`go test -race ./...`、`go vet ./...`と整形確認を行う。追加テストはルーム分離、席の競合、権限、キー、死亡時の競合、SSE復旧など実際の振る舞いに重点を置く。UIはキーボードと上記サイズで実操作する。設定追加・ポート変更・AI通信拡張に合わせて全配布設定、Docker、日英API/設定/プロトコル文書を更新する。
